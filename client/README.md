# DiveVision client

The single DiveVision client: Expo (React Native + TypeScript) with Expo Router, shipped first as
a web app (react-native-web) and built to be published to the app stores later (EAS
Build/Submit). It serves the app half of the project — see `../CONTEXT.md` for the vocabulary
(User, Photo, Original, Enhanced Image, Photo Status).

## Screens

| Route          | File                          | What it does                                                          |
| -------------- | ----------------------------- | --------------------------------------------------------------------- |
| `/sign-in`     | `src/app/sign-in.tsx`         | Sign in or sign up (email + password, Supabase Auth). Sign-up is open. |
| `/`            | `src/app/(app)/index.tsx`     | Gallery of my Photos with live Photo Status; upload a photo.          |
| `/photos/[id]` | `src/app/(app)/photos/[id].tsx` | One Photo: before/after comparison once enhanced; delete it.        |
| `/account`     | `src/app/(app)/account.tsx`   | Sign out; delete my account (and every Photo).                        |

`src/app/_layout.tsx` guards the routes with `Stack.Protected`: without a session only
`/sign-in` exists, with one only the `(app)` group does.

## Data flows

- **Reads come straight from Supabase** (`src/lib/photos.ts`): the gallery, single Photos and
  signed image URLs (1 h). Every query filters `user_id = <signed-in User>` explicitly instead of
  relying on RLS alone, so Photos made public later never leak into a User's gallery; storage
  paths outside the User's own folder are never signed.
- **Live status over Supabase Realtime**: `postgres_changes` on `photos` filtered by
  `user_id=eq.<User>` (`subscribeToMyPhotos`); the gallery and Photo screen refetch whenever the
  channel (re)connects to catch up on missed changes.
- **Writes go through the API** (`src/api/client.ts`): `POST /photos/` (upload, answers
  `pending` at once), `DELETE /photos/{id}/`, `DELETE /account/`, each with
  `Authorization: Bearer <Supabase access token>`.

## Configuration

Copy `.env.example` to `.env`. The client holds only public values — the Supabase URL, the
publishable (anon) key and the API URL — and refuses to start with a secret/service-role key.
`EXPO_PUBLIC_*` values are compiled into the bundle, so change them and rebuild.

## Running it

```sh
npm ci
npm run web        # Expo dev server on http://localhost:8081
```

Or the static web build via Docker Compose from the repo root (reads `SUPABASE_URL`, the
publishable `SUPABASE_KEY` and `CLIENT_API_URL` from the root `.env`):

```sh
docker compose up --build api worker client   # client on http://localhost:8081
```

The API's `CORS_ALLOWED_ORIGINS` must include the client's origin (`http://localhost:8081` by
default).

If the Supabase project confirms emails on sign-up, set its Auth **Site URL** to the client's URL
so confirmation links land back in the web app, which then signs the User in.

## Checks

```sh
npm run lint
npm run typecheck
npm test           # offline: Supabase and the API are faked
npm run api:check  # src/api/schema.d.ts matches openapi.json
```

## The generated API client

`src/api/schema.d.ts` is generated by [openapi-typescript](https://openapi-ts.dev) from
`openapi.json`, FastAPI's schema for `divevision/src/app/main.py`; `src/api/client.ts` wraps it
with `openapi-fetch`. Never edit either generated file by hand. After changing the API:

```sh
npm run api:update   # = api:export (poetry, writes openapi.json) + api:generate
```

CI fails when either is stale: pytest checks `openapi.json` against the app, and the `Client`
workflow checks `schema.d.ts` against `openapi.json`.
